# PANADERO Baking System — How It Works

## 1. Big-picture architecture

```text
Customer HTML/JS ─┐
Staff HTML/JS    ─┼── HTTP/JSON ──> Node.js + Express API ──> MySQL database
Admin HTML/JS    ─┘
```

The HTML and CSS are the presentation layer. The JavaScript files collect user actions and call the Node.js API. The Node.js API is the only layer that talks directly to MySQL.

> The browser does not connect directly to MySQL. This protects database credentials and ensures prices, stock, permissions, and totals are validated on the server.

## 2. Starting the system

1. The supplied SQL creates the `panadero_bakery` database and the core tables.
2. `server.js` creates two compatibility tables when the server starts:
   - `reservations` — reservation requests are not present in the supplied SQL.
   - `inventory_batches` — fresh baking batches are not present in the supplied SQL.
3. If the catalog is empty, the server inserts the four default categories and the existing bakery products.
4. Express starts on port `3000` by default.
5. Express serves the three existing frontend folders:
   - `/customer`
   - `/staff`
   - `/admin`

## 3. Role-based login

Open `/login.html` for the separate login page. The server checks the account role and redirects to the correct portal:

- `Customer` → `/customer/index.html`
- `Staff` → `/staff/staff-dashboard.html`
- `Admin` → `/admin/admin.html`

The staff and admin pages have guards that redirect unauthenticated users back to login. Customer orders and reservations require a signed-in customer token. For local testing, the server creates `staff@panadero.local` / `Staff123!` and `admin@panadero.local` / `Admin123!` if they do not already exist.

## 4. Customer flow

### Browse products

1. `menu.js` asks `ProductService` to refresh the catalog.
2. `product-service.js` calls `GET /api/catalog`.
3. The API reads `categories` and `bread_products` from MySQL.
4. The API returns products with their current stock.
5. The existing customer HTML renders the returned products without changing the page design.

### Register or log in

1. The customer submits the existing login or registration form.
2. `auth-service.js` sends the form data to `/api/auth/login` or `/api/auth/register`.
3. The API checks the user in `users`.
4. Passwords are stored as bcrypt hashes in `users.password_hash`.
5. The API returns a temporary session token and basic user data.
6. The browser stores the session data in `localStorage` and sends the token as a Bearer token on protected requests.

### Place an order

1. The cart remains in the browser until checkout.
2. Checkout sends only product IDs and quantities to `POST /api/orders`.
3. The API reloads product prices from MySQL instead of trusting browser totals.
4. The API locks/checks the requested products, verifies stock, calculates the total, creates an `orders` row, and creates one `order_items` row per product.
5. The API deducts stock from `bread_products.stock_quantity`.
6. The customer receives an order reference such as `ORD-00001`.

### Place a reservation

1. The reservation page sends the selected product, quantity, customer, date, and time to `POST /api/reservations`.
2. The API validates the product and stock, calculates the total, creates a `reservations` row, and deducts stock.
3. The customer receives a reference such as `RES-00001`.

### View personal activity

1. The tracking page calls `GET /api/orders` and `GET /api/reservations`.
2. The API uses the logged-in user's ID, so customers only receive their own records.

## 5. Staff flow

The supplied staff pages do not contain a staff login screen, so staff endpoints are available to the existing staff portal. In a production deployment, add staff authentication before publishing the portal publicly.

### Inventory

- `GET /api/inventory` loads products, categories, stock, and baking batches.
- `PATCH /api/inventory/products/:id/stock` changes the current product stock.
- `POST /api/inventory/batches` stores a fresh batch in `inventory_batches` and increases `bread_products.stock_quantity`.

### Orders and reservations

- `GET /api/staff/requests` loads all orders and reservations for the staff table.
- `PATCH /api/orders/:id/status` changes an order status.
- `PATCH /api/reservations/:id/status` changes a reservation status.

The frontend status flow is:

```text
Pending → Preparing/Processing → Ready → Completed
```

## 6. Admin flow

The admin page is a single-page interface. Its current HTML/CSS shell is generated by the existing `admin.js` and was not redesigned.

1. On load, it requests `GET /api/admin/state`.
2. The API sends the catalog, users, orders, reservations, batches, and stock.
3. Existing admin tables and dialogs render that data.
4. When an admin changes products, categories, users, stock, or statuses, `admin.js` sends the current state to `POST /api/admin/sync`.
5. The API writes the changes to MySQL.

## 7. Database responsibilities

| Table | Purpose |
|---|---|
| `users` | Customer, staff, and admin accounts |
| `categories` | Product categories such as Breads and Cakes |
| `bread_products` | Product name, price, category, and current stock |
| `orders` | Customer order header, total, status, and date |
| `order_items` | Products and quantities belonging to an order |
| `reservations` | Reserved product, schedule, total, status, and customer |
| `inventory_batches` | Each fresh batch baked by staff |
| `system_logs` | Available for future audit logging |

## 8. Important relationships

- One user can have many orders.
- One user can have many reservations.
- One category can contain many products.
- One order can contain many order items.
- One product can appear in many order items.
- One product can have many inventory batches.
- One product can be reserved many times.
- Deleting an order deletes its order items because of `ON DELETE CASCADE`.
- Products/categories/users are protected by foreign keys so the database does not silently lose related records.

## 9. Example order transaction

For a customer ordering two croissants:

```text
1. Browser sends: product_id = 2, quantity = 2
2. API reads croissant price and stock from bread_products
3. API confirms stock_quantity >= 2
4. API inserts orders(total_amount = price × 2)
5. API inserts order_items(order_id, product_id = 2, quantity = 2, unit_price)
6. API updates bread_products.stock_quantity = old stock - 2
7. API commits all changes together
```

If any step fails, the transaction rolls back so the database does not contain a half-created order.

## 10. Files to know

- `server.js` — Express routes, MySQL queries, validation, and migrations
- `package.json` — Node.js dependencies and start commands
- `database/panadero.sql` — supplied base database schema
- Customer `assets/js/*-service.js` — API adapters used by customer pages
- Staff `assets/js/staff-data.js` — API adapter used by staff pages
- Admin `assets/js/admin.js` — existing admin UI plus API hydration/synchronization
- `.env` — local database credentials; do not commit this file

## 11. Security notes for a real deployment

- Add a staff/admin login and enforce role authentication on staff/admin endpoints.
- Replace the in-memory session map with a persistent session or JWT strategy.
- Store customer mobile numbers in a dedicated column if they must be retained.
- Add rate limiting, HTTPS, CSRF protection, and stronger audit logging before production use.
- Never expose `.env` or MySQL credentials to the browser.
